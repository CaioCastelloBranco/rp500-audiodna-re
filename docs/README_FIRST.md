# RP500 Archive — GSP1101 User-IR Cabinet Port Feasibility

**Project:** Assess whether the GSP1101 user-cabinet (IR) feature can be ported to the DigiTech RP500, and build as much of it as the hardware allows.

**Start here if you are new:** `00_master/PROJECT_STATE.md` (what is done, what is open, what to do next) and `00_master/TOOLCHAIN.md` (every tool, how to restore it, how to run every check). Attribution for the models and tools that produced this work: `00_master/CREDITS.md`.

**Archive date:** 2026-11-11

**Size:** ~220 MB across 10 folders + 334 analysis scripts

**Version control:** this folder is a **git repository** (`main` branch, baseline
tag `baseline-2026-11-11`). Every file is stored byte-exact
(`core.autocrlf false`), so the analysis can be replayed against exactly the
bytes that were analysed. `git log` / `git diff` / `git show <rev>:<path>` all
work as usual; the routine is documented in `00_master/TOOLCHAIN.md`
("Version control").

**Versions are also kept in the folder**, under `99_snapshot/` — one folder per
version with a SHA-256 manifest, plus one cumulative `project.bundle` holding
the full history. Cut a new one with
`python 04_analysis_scripts/cut_snapshot.py`, list them with `--check`. The
whole scheme, the copy-and-audit procedure and the reading order are in
**`00_master/AUDIT_GUIDE.md`**.

> The repository was created **after** the 2026-11-11 revision, so its first
> commit is a *baseline* of the corrected state rather than a history. The
> claims that changed in that revision, with a discriminating test for each,

**Image layout notes:**
- GSP1100 images (`c48`, `c63`, `gsp1101_fw.bin`) are `0x100080` bytes: `body0` + 15 × (8-byte descriptor `00 kk 00 00 00 01 00 00` + `body`) + 8-byte trailer. The 8 bytes at the start of each body are a code stub, not a header.
- RP500 / V20 images are flat `16 × 64 KB` bodies with descriptors stripped.
- Bank-entry stubs (first 8 bytes of each body): V20 `EA 80 68 02 2E C5 53 91`; C48 `EA 80 68 02 30 83 53 91`; C63 `EA 80 68 02 30 7A 53 91`; RP500 `EA 00 02 00 6B 53 91 DF`.
- **rp500_fw.bin is NOT byte-identical to v20_res_51E18.bin** (they share stub prefix but are different builds). rp500_fw.bin == reassembled `rp500V20.DigBin`.

### Address convention used throughout this archive

Quoted addresses are `bank k offset X`, where the bank body view is the concatenation of the 16 × 64 KB bodies:

- **Flat images** (V20, RP500): body *k* occupies file bytes `[k·0x10000, (k+1)·0x10000)`.
- **Interleaved images** (C48, C63): body *k* occupies file bytes `[k·0x10000 + k·8, k·0x10000 + k·8 + 0x10000)` — the `k·8` shift is the space taken by the 8-byte descriptors of banks 1…*k*.

`X` is measured from the start of that body region, so a "flat" figure quoted as `k·0x10000 + X` differs from the true file offset by `k·8` for the interleaved images. `verify_all.py` (project root) checks every quoted address in exactly this convention.

### What each document settled (mined 2026-11-11, report §13.9)

| Document | What it answered |
|---|---|
| `GSP1101 RELEASE NOTES VERSION C54.txt` (line 303ff) | the user IR is **mono** (first 128 samples of the **left** channel), the **same IR goes to both outputs**, and it sits at the **head of a fixed-length block** ("remove any 0's at the beginning") |
| `gsp1101 release notes version c63.txt` (lines 335–397) | the whole workflow: position the preset on a user cab → Jcabinet → **gain setting** + **cabinet position** → **audition** (no reboot) or **store** (flash + reboot) → interruption can cost a factory reset; 10 positions; user cabs bypass the ¼" outputs; a new LPF parameter for user cabs |
| `RP500_OM_EN.txt` (lines 218, 1929) | the RP500 has a **single AudioDNA2 chip**; **100 user presets** (so a user-data area exists); the firmware cab list **is** the manual's list |
| `GSP1101 Signal Flow.txt` | external audio routing only (mono effects, stereo dry summed) — *not* the IR path; it does not contradict "same IR to both outputs" |
| `C25` / `final C36` release notes | no mention of user cabs at all — brackets the feature to C54+ |
| `netupdater_strings.txt` | updater strings: RP500 ProductID `0x5`, revisions 1.2/1.4/2.0 (now also decoded from the binary itself) |

The protocol details recovered by reverse engineering are **confirmed** by the
literature: the commit flag is the audition/store bit, the gain is a dB value
applied at upload, there are 10 slots, and the upload targets the currently
selected slot.

## Key Findings (Synthesized)

### Verdict
- **Host/firmware side: feasible, and the protocol is recovered.** Cab table, UI, 10 slots, WAV→record conversion, the RP500's own preset protocol (`MOVE_PRESET` 0x39, `RECEIVE_PRESET_PARAMETERS` 0x2D — see `06_deliverable/rp500_preset_protocol.md`) and `.DigBin` redeployment are all known. **Slot storage is not host-side** — see the correction below.
- **DSP/IR engine side: unproven — the only gating blocker.** The RP500 and the GSP1101 share the host↔DSP interface (23 addresses in common, below), so the *register set* is not the obstacle; what is unproven is that the RP500's part accepts a **variable-length** block **and convolves with it**.
- **Overall: not a practical patch-the-firmware port today.** A DSP capability test on hardware is the decisive next step (roadmap S3).
- **Correction (2026-11-11):** the port is **not** a `MOVC`→`MOVX` source swap. The RP500's DSP payload is a 24-byte parameter descriptor; the GSP's user cabinets ride on a separate, variable-length, XRAM-sourced, `0xF5`-terminated stream the RP500 does not have. Report §13.10.
- **Correction (2026-11-11, storage):** there is **no host-side persistent store** — the flash is 1 MB and an update rewrites all of it, and there is no XRAM store. The preset store is the **device's**, reached over the preset protocol; its physical medium is still being pinned (`rp500_storage.md`, `rp500_preset_protocol.md`).

### Shared Architecture (8051 host)
- Both devices: 16-bank 8051 flash, 1 MB, AudioDNA2T DSP family, 44.1 kHz sampling.
- **23 host/DSP addresses are common to all three images** (RP500 v2.0, GSP C48, GSP C63), including the complete handshake set: the DSP-window registers `0xD01E/1F/20`, `0xD034`, `0xD050`, `0xD05A/5B`, `0xD066/69/6D/6E/6F`, `0xD070` and the command ports `0xE000/0xE200/0xE400/0xE800`. The two products therefore share the *interface*; they differ in **which of its features they use**, not in whether it exists.
- Shared 25 speaker-cab model names (`CHAMP1X8 … DIGISPKR`) plus `DIRECT`, `DREAD AC`, `JUMBO AC`.
- RP500 has **no** `USER` slots, no `USER_CAB`, no `CAB_EN_XLR_LPF`.

### DSP Command Sets (disassembly-verified, `d51.py`)

| Register | GSP1101 (V20/C48/C63) | RP500 |
|----------|----------------------|-------|
| `0xE200` | 1, 2, 4, 8, 0x10 | 1, 2, 3, 4, 8, 0x10, 0x20 |
| `0xE400` | 1, 0x40, 0x80, 0xC8, 0xFE | (none observed) |
| `0xE800` | 0xA0, 0xA4, 0xA9, 0xAF, 0xB8, 0xC0 | (none observed) |
| `0xD066` | 6, 7, 0x84, 0x86, 0x87, 0x8B (V20 also 0x85, 0x98) | 4, 5, 6, 7, 0x0B, 0x18 |
| `0xD070` refs | 104 | 6 — of which only **2** are stores (`MOV DPTR,#0D070h ; MOVX @DPTR,A`), one per cabinet bank |
| `0xD05A` refs | 24 | 19 |

Method: every `MOV DPTR,#<reg>` site is located and the next `MOV A,#imm` is read from the **disassembly** (`d51.py`), not from a raw byte scan — a byte scan yields false positives because `0x74` can appear as an immediate operand rather than an opcode.

C63 added **no new** host→DSP command vs C48/V20 (it removed two `0xD066` writes, `0x85` and `0x98`). The IR payload must travel over a pre-existing path.

### No Factory FIR Tables
A strict scan (smooth sequence, |v| < 2²⁴, ≥100 non-zero taps, front-loaded energy) found **zero** 128-tap coefficient blocks in C48, C63, RP500, or V20. Factory cabs are DSP-resident parametric models, not swap-in coefficient tables. A user cab needs arbitrary 512-byte coefficients — a different data path.

### User-Cab Record Format (fully verified, encoder selftest passes)
Total **2048 bytes** (`0x800`):

| Offset | Size | Contents |
|--------|------|----------|
| `0x000` | 4 | `00 5C 00 05` (container magic; built as 32-bit immediate, never appears literally in firmware) |
| `0x004` | 8 | `00 05`, `cabIdx*8`, `00 00 00 08 00` |
| `0x00C` | 4 | tap count, BE32: `0x80` = 128; `0xD0` = 208 (option bit) |
| `0x010` | N×4 | N × signed 32-bit BE coefficients (N = tap count) |
| `0x210`/`0x350` | … | `0xFF` fill up to `0x7E7` |
| `0x7E7` | 23 | filename record, NUL padded |
| `0x7FE` | 2 | `[cabIdx, flag]` |

**Scaling:** 16-bit `s << 12`, 24-bit `s << 4` → 28-bit full scale; × linear gain `10^(dB/20)`; round; clamp to int32.
**WAV rules:** RIFF/WAVE, `fmt ` size `0x10`, PCM format 1, 1–2 ch, **44100 Hz only**, 16/24/32-bit, valid `data` chunk; first 128 left-channel frames (right discarded); option bit raises cap to 208.
**Transport, GSP1101 (the reference):** USB-MIDI SysEx via HMG `Super7TxSysexMsg`, **chunked**: handshake (`0x01`), then one `0x7A` message per `0x100`-byte chunk (`<addr32 BE> <len16 BE> <packed data>`), then one `0x73` commit (`30 01 <cabIdx> <flag>`). Header is `F0 00 00 10 00 5E 05` and is read from the device's handshake reply, not hardcoded. Payload is Super7-packed (1 MSB byte per 7 bytes) and terminated with `XOR(after F0) & 0x7F` + `F7`. Full detail: `06_deliverable/gsp1101_to_rp500_feasibility.md` §11.6–11.7.

**Transport, RP500 (what the port must use):** the device's **own** preset protocol — *not* the GSP's framing above. gdigi (`07_open_source_tools/gdigi/`) is a working client: `MOVE_PRESET` (`0x39`) with `<srcBank> <srcIndex> <dstBank> <dstIndex> <name>\0 <flags>` saves a slot; `RECEIVE_PRESET_PARAMETERS` (`0x2D`) fills the edit buffer; `REQUEST_PRESET` (`0x2A`) pulls one back. No Super7, no XOR checksum. **All 12 of gdigi's message IDs are in the RP500 firmware's dispatch table** (bank 7 `0x699E`). Detail: `06_deliverable/rp500_preset_protocol.md`.

### Flash Headroom
`0xFF` free-space census (runs ≥ 256 B), per build:

| Build | Total free | Largest contiguous |
|-------|-----------|-------------------|
| GSP1101 V20 | `0x2889A` (166,042 B) | `0x8431` (33,841 B) |
| GSP1101 C48 | `0x7135` (28,981 B) | `0x155F` (5,471 B) |
| GSP1101 C63 | `0x4E19` (19,993 B) | `0x14FB` (5,371 B) |
| **RP500** | **`0x277BA` (161,722 B)** | **`0x5FD0` (24,528 B)** |

Note the IR build (C63) has *less* free flash than the pre-IR builds — the user-cab feature consumed some of it. The RP500 still has ~8× the C63 headroom.

> **But free flash is not usable storage.** The updater's all-`0xFF` skip applies **only inside segment 0**; every empty block in segments 1–15 is written on each update, including the RP500's `0x5FD0` run at `A030`. So that run is good for **stub code that ships with the firmware**, not for user data. Measured: 4 039 of 4 096 blocks sent, 57 skipped, all in segment 0 (`rp500_storage.md` §1).

### Deployment Path (known in principle)
`NetUpdater 1.0.1` supports RP500 (ProductID `0x5`, revisions 1.2/1.4/2.0), fetches `UpdateTargets.xml` over HTTP (redirectable). `.DigBin` container = 12-byte header + bodies + descriptors; **no checksum/signature visible**. A patched RP500 flat image can be repackaged and served from a local `UpdateTargets.xml`. Bootloader validation is **not a bricking hazard**: per the open-source uploader's author, an image that does not run causes the unit to fall back to the bootloader's flashing process. That claim is **reported, not experimentally tested** — deliberately flashing a broken image to prove it is off the table. It is instead analysed statically, and every build stays a minimal delta from stock. See `06_deliverable/rp500_firmware_roadmap.md`.

### Updater Integration (done, flashed 2026-11-10)
The supplied updater is a `NetUpdaterClone` .NET 10 single-file bundle that carries its images and `UpdateTargets.xml` as manifest resources. A patched copy is at `09_builds/updater_2.1/`: the RP500 gained revision **2.1** (same-length edits only) carrying the renamed-cabinet build. `MainForm.BuildRevisionList` only offers revisions strictly newer than the version the device reports, which is why the build is labelled 2.1 rather than reusing 2.0. The original exe is untouched; the wizard's "SAFE TEST MODE" checkbox verifies the handshake without writing. **Verified on hardware**: dry run + real write, 4,039 blocks, unit boots with `CAIO4X12` (see `05_evidence/2026-11-10_rp500_updater_flash.log`). Full walkthrough: `09_builds/updater_2.1/README.md`.

## Decisive Test Plan

The decisive test is whether the RP500's DSP takes a **variable-length block
and convolves with it**. Two halves, both unmeasured (roadmap **S3**; report
§13.10):

- **G1** — does the AudioDNA2 accept a length-bounded, `0xF5`-terminated block?
- **G2** — does it *render* that block as a convolution? This is the sharper
  half: there are **no factory IRs** (factory cabs are parametric models), so
  an IR is a different kind of data and a parametric-only DSP cannot render it.

The cheap path is: simulator first (the bench exists —
`rp500_ucsim_stream.py`), then a minimal build that sends 512 bytes followed by
`0xF5`, and is listened to.

**Already tried, and closed** — the earlier hardware probe, kept for the record:

1. **Connect the RP500 to a Linux host over USB-MIDI** and verify the device is visible (`lsusb`, `amidi -l`, `aconnect -l`).

2. **Build gdigi** from `07_open_source_tools/gdigi/` (C + GTK + ALSA raw MIDI).

3. ~~**Probe `AMP_CAB_TYPE`**~~ **Done on hardware** — indices 570–626 are accepted (factory limit 585 is a UI constraint only), but every accepted change sends just the 2-byte parameter value; no coefficient block is transferred. See the hardware section below.

4. ~~**If extended values are accepted, send the record**~~ **Done** — the 2048-byte record from `usercab_encode.py` was transmitted successfully, but produced no audio/DSP confirmation and there is no UI slot to select it. The cab-select path is therefore **closed as an IR path**: the device takes an index and sends a 24-byte descriptor, not IR data. That is what forced the port spec away from "source swap" (§13.10).

### Note on the `04_analysis_scripts/` scripts

All ~155 scripts are **portable**: none contain absolute personal paths. Artifact
locations are resolved relative to the project root by three helpers prepended to
each file:

- `_P("name")` — resolves a named artifact: `.bin` → `01_source_firmware/`,
  `.exe` → `02_source_binaries/`, `.pdf` → `03_docs/`; unknown names fall back to
  the script directory. Two legacy aliases map older names onto the archive
  (`gsp_fw.bin → gsp1101_fw.bin`, `rp_fw.bin → rp500_fw.bin`).
- `_FW` — path of `01_source_firmware/` (used by the prefix-style scripts).
- `_OUT(name)` — derived/output files (`'wb'` writes, `%X` scratch names, `.txt`
  dumps) go to the script directory so the archive is never overwritten.

Two things to know before reusing them:

1. **"wb" scripts are extractors.** `extract_c48.py`, `cmp3.py`, `gsp_deep.py`
   re-derive `c48_fw.bin` / `c63_fw.bin` / the bank-joined images from the
   source `.DigBin`/updater containers and write them via `_OUT()`. Run them
   only if you want to regenerate those images; never point them at the
   archive's `01_source_firmware/`.
2. **The `payload16()` helper** used by many of them (`gsp_diff.py`, `usercabxref.py`, `verify_report.py`, …) slices `img[k*0x10008+8 : (k+1)*0x10008]`. For *k* > 0 that window is 8 bytes late relative to the true interleaved layout (`body_k` is at `k*0x10000 + k*8`), so it yields each bank shifted by 8 bytes and overruns into the next descriptor. **Use `verify_all.py`'s `docview()` instead** when checking bank-relative addresses; the offsets quoted in this archive are correct for the true layout.

The `d51.py` disassembler is the authoritative tool for instruction-level work — the raw byte-scan heuristic used by `cmdvals.py` produces false positives on `0x74` immediates.

## Hardware Test Results (Physical RP500)

Test performed on a physical DigiTech RP500 connected via USB-MIDI to a Linux host. Device identified as `DigiTech RP500:DigiTech RP500 MIDI 1` (ALSA port index 1).

### Device Connection

- **Connection:** USB-MIDI (ALSA raw MIDI)
- **Device detection:** Confirmed via `lsusb`, `amidi -l`, `aconnect -l`
- **gdigi operation:** Successfully built and ran; able to control the unit and read parameters
- **Device port:** `hw:2,0,0` (ALSA card 2, device 0, subdevice 0)

### Cabinet Index Range — Empirical Testing

Cabinet type parameter `AMP_CAB_TYPE` (ID **2560**, position **9**, channel A) was probed via SysEx `get_option`/`set_option`.

| Value Range | Result | Display Names Confirmed |
|-------------|--------|------------------------|
| 570–585 | ✅ Accepted | Direct, Champ® 1x8, Deluxe® 1x12, Deluxe Reverb 1x12, Twin 2x12, Blonde 2x12, Bassman 4x10, Boutique 4x12, Fane 4x12, DigiTech® Spkr Comp, and others |
| 586–626 | ✅ Accepted | DigiTech® Spank 2x12, DigiTech® Solo 4x12, DigiTech® Bright 2x12, DigiTech® Chunk 4x12, British 2x12, British 4x12, British Green 4x12, DigiTech® Metal 4x12, DigiTech® Rock 4x12, DigiTech® Alt 4x12, DigiTech® Vintage 4x12, Vintage 4x12, British 1x12, GA 1x12, Recto 4x12, Jazz 2x12 |
| 627+ | ❌ Not valid | Value 627 (listed as `JBL 2x15` in gdigi.h) does not correspond to any cabinet on this RP500 unit; higher values not tested |

**Conclusion:** The RP500 DSP accepts cabinet parameter values beyond the factory UI range of 585, up to at least 626. The factory limit of 585 is a UI constraint, not a DSP constraint.

### Custom IR Record — Encoding and Transmission

A custom cabinet impulse response was encoded and transmitted:

| Item | Value |
|------|-------|
| Source WAV | `IR/MesaV3022.wav` — 44.1 kHz, PCM, mono, 24-bit, 208 samples |
| Encoder | `usercab_encode.py` (C59 reimplementation) |
| Output record | 2048 bytes (`0x800`) |
| Slot | 1 |
| Gain | 0 dB |
| Taps | 208 |
| Transport | USB-MIDI SysEx (`F0` + payload + `F7`) |
| Transmission result | ✅ Message sent successfully (no transmission error) |
| DSP acceptance | ❓ **Unconfirmed** — no observable audio change, display update, or `RECEIVE_PARAMETER_VALUE` response confirming processing |
| User cab UI slot | ❌ None exists in factory firmware; no way to select or activate the transmitted record |

### Key Findings from Hardware Testing

1. **DSP accepts extended cabinet indices** — Values 586–626 were accepted and produced expected cabinet names. The DSP is not hard-limited to 585.

2. **SysEx transport works** — The RP500 receives and responds to SysEx parameter messages. `RECEIVE_PARAMETER_VALUE` responses were observed for valid factory/extended cabinet indices.

3. **No user cab subsystem in factory firmware** — The RP500 has no `USER 1`–`USER 10` strings, no `USER_CAB %D` handler, no `CAB_EN_XLR_LPF` parameter, and no UI menu for user cab slots. A transmitted 2048-byte custom IR record has no activation path. *(Note 2026-11-11: the RP500 does have a numeric-ID **preset** service — `MOVE_PRESET` 0x39 — which gdigi drives; see `06_deliverable/rp500_preset_protocol.md`.)*

4. **gdigi.h enum values are not all valid on RP500** — Value 627 (`JBL 2x15` in gdigi.h shared enum) does not exist on this RP500 unit. gdigi supports multiple DigiTech products; not all enum values apply to every model.

5. **Firmware flash path verified end to end** — A patched `.DigBin` (cab 24 `DIGISPKR` → `CAIO4X12`, 8 bytes) bundled into the updater as revision **2.1** flashed cleanly on 2026-11-10: 4,039 data blocks in 7 m 03 s, one NAK retried, no safety stops. The unit boots and the device cab menu shows `CAIO4X12`; X-Edit is unchanged (it uses its own name table). Log: `05_evidence/2026-11-10_rp500_updater_flash.log`.
